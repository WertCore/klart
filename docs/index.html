klart

Brightness for every display attached to the machine — the built-in panel and external monitors alike, from the menu bar or the command line.

And when a monitor will not dim, it tells you why.

v0.3.0 macOS · Linux · Windows MIT or Apache-2.0 Source on GitHub

Install

Homebrew covers macOS (Apple silicon) and Linux (x86_64).

brew install wertcore/tap/klart   # no quarantine, nothing to unblock

On macOS, one more line is worth it if any display falls back to software dimming — macOS reverts a gamma ramp the moment the process that set it exits, so the menu bar agent is the thing that holds it. klart list marks those displays with a *.

brew services start klart

That, rather than klart autostart on: autostart registers an application bundle with macOS, and a Homebrew install has no bundle — only the two binaries. klart autostart is for the app from the archive below.

Nothing to clear, and no flag to pass for it. Homebrew’s formula downloader does not set the quarantine attribute, so there is nothing to undo. Quarantine is applied by browsers and LaunchServices — which is why a zip downloaded from the releases page needs clearing and this does not.

If you went looking for --no-quarantine: it was a cask option, it was deprecated in October 2025 and the last of it was removed from Homebrew in July 2026. Passing it to Homebrew 7 is Error: invalid option, whether the target is a formula or a cask.

Or the archives

Every release carries a macOS app bundle, a Linux tarball and a Windows zip — on the releases page. A bundle that arrived through a browser is quarantined, and klart is not signed or notarised, so:

xattr -dr com.apple.quarantine /Applications/Klart.app

When a monitor will not answer

Some monitors cannot be dimmed over the wire, and the usual answer is a list of things to try: another cable, another port, a setting in the on-screen menu, a different application. klart probe measures instead.

$ klart probe
LS32AG55x (SAM-71e3-HNAW900001)
  Core Graphics id 2
  registry node    matched
  link             DP -> HDMI
  I2C channel      published
  ok               read 128 bytes at the EDID address (0x50): valid EDID header, version 1.3
  failed           read the same 128 bytes at the DDC/CI address (0x37): byte for byte
                   identical to the EDID address — the chip address is being ignored
  failed           DDC/CI Get VCP 0x10 (chip 0x37, offset 0x51): 0xe0114102

  EdidOnly
  This link serves a cached copy of the monitor's EDID and does no I2C:
  reads return the same bytes whichever address they ask for, and every
  write is refused. Nothing here ever reaches the monitor, so this is not
  the monitor's DDC/CI setting and no software can change it — the
  monitor is never asked. Use a link with no conversion in it: USB-C to
  DisplayPort, into the monitor's DisplayPort input.

Built-in Display (builtin)
  ...
  ok               read the same 128 bytes at the DDC/CI address (0x37): differs from
                   the EDID address, so the address is honoured
  ...

Corroborated on this machine: Built-in Display honoured the I2C chip
address and LS32AG55x ignored it, through the same calls in the same
process. The difference is the link, not the interface.

Every line is something that was attempted, with what came back. The verdict is derived from those attempts and nothing else:

Answers

DDC/CI is working. If brightness still will not move, the problem is elsewhere.

MonitorDeclines

Two addresses answered differently, so transactions are reaching the monitor — and it is refusing DDC/CI itself. Most ship with it off. Turn on DDC/CI, Monitor Control, External Control or PC Control in its own menu.

EdidOnly

The link serves a cached EDID and does no I2C. The monitor is never asked, so this is not its DDC/CI setting and no software can change it. Use a link with no protocol conversion.

NoI2c

Nothing could be read over this link at all, not even the EDID. Something between the machine and the monitor is not passing I2C.

NoChannel

No I2C channel on this machine at all — what a virtual screen looks like: AirPlay, Sidecar, DisplayLink. None carry DDC/CI by design, and klart falls back to software dimming.

HdrInTheWay

The display is in HDR, and brightness control did not answer. Those go together: an HDR picture mode commonly pins brightness or stops honouring the feature. Windows only.

NotApplicable · Unclear

The built-in panel, which has its own mechanism — or attempts that fit no known pattern, in which case the output above is the evidence.

The last line of the output is the control, and it is what makes the verdict a measurement rather than a guess. Two displays, the same calls, the same process: if one honours the I2C chip address and the other ignores it, the interface works and the difference is the link.

New in 0.3.0

Driven by what people ask the other tools for, counted from their issue trackers.

Levels go back after a sleep

Brightness coming back wrong after a sleep is the single most-complained-about behaviour in this category. The reason it is hard is that a display does not answer the instant the machine wakes — the link returns before the panel behind it, and a write sent then is accepted and dropped with no error. So klart writes, reads back, and keeps trying until the display agrees.

Scroll the menu bar icon

A wheel or a trackpad over the icon, without opening anything. It moves every display by the same amount from wherever each one is, so two displays balanced against each other stay balanced.

Keep the displays’ relative brightness

The all-displays slider is absolute by default: every display goes to the level shown. :combined = relative moves them all by the same amount instead, measured from where they were when the menu opened — so a display that pins at one end comes back to where it started rather than quietly losing the difference.

The probe names HDR

On Windows, HDR takes brightness control away without saying so. The probe now says so instead of reporting Unclear.

Why this is three mechanisms rather than one

There is no single brightness API on any of these systems, so there is no single backend here.

DisplayMechanism
Built-in panelDisplayServices on macOS, WMI on Windows, /sys/class/backlight on Linux
Speaks DDC/CIVCP feature 0x10 — IOAVService I2C on macOS, dxva2 on Windows, /dev/i2c-* on Linux
Everything elseA gamma ramp. Darkens the picture rather than the backlight, so it is a fallback rather than a peer. macOS reverts it when the process exits, which is why the agent exists. No equivalent on Linux without a display server.

Only the platform layer knows which operating system this is. Brightness, the display key, the DDC/CI protocol and the resolution order are written once and shared — which is what makes a configuration file written on macOS name the same monitors on Windows.

What has actually been run

Worth stating plainly rather than leaving to be discovered.

PlatformState
macOSMenu bar agent and command line, run on real hardware. Apple silicon only.
LinuxCommand line, compiled and tested by CI, never run.
WindowsCommand line, compiled and tested by CI, never run.

That table is about platforms. Individual features can be newer than the hardware they have been tried on — in 0.3.0, nobody has yet scrolled the menu bar icon, no HDR monitor has seen the HDR verdict, and the wake restore has not been checked across a real suspend. PLAN.md records this per feature, one entry per change, with its own unticked boxes.

The command line

klart list                    # every display, its level, and how klart reaches it
klart set 60
klart down 10 --display LS32
klart up --all
klart get --json
klart probe                   # why won't this monitor answer?
klart restore
klart rename 1 "Desk monitor"
klart autostart on

Commands act on the main display — the one with the menu bar, on macOS — unless told otherwise. --display takes an index, a key, or part of a name.

Levels are remembered per display rather than per port, keyed off EDID, so they survive a reconnect — and the file is meant to be edited by hand.
